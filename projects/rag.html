Conversational RAG Knowledge Assistant

A reusable Retrieval-Augmented Generation system that combines semantic search, vector storage, conversation memory and language-model inference. It works as an importable Python module or as a separately deployed HTTP API.

01 / Overview

Answers grounded in your own knowledge base.

The application retrieves relevant chunks from a curated knowledge base and hands them to an LLM as context, instead of relying only on the model's pretrained knowledge.

🧠

Knowledge-grounded answers

Relevant text chunks are retrieved first, then the LLM generates an answer using that retrieved context.

💬

Conversational context

Each conversation is identified by a user_id and session_id. Recent turns help resolve follow-up questions.

🧩

Reusable RAG core

Retrieval and generation sit behind a service boundary. Call it directly from Python or expose it through FastAPI.

🖥️

Local and network usage

Ollama runs models on the host, Qdrant stores vectors, and the Streamlit UI can run on another machine over a trusted network.

Core idea: RAG = retrieve relevant knowledge first, then generate an answer from it. Vector search and the language model play different roles in the pipeline.

03 / Integration

Three ways to use the same project

Different integration boundaries, shared RAG concepts.

Direct module integration

A Python application imports the RAG package and calls its service methods directly. No HTTP hop is needed between the caller and the RAG service.

from rag_module import RAGService, RAGConfig

config = RAGConfig(...)
rag = RAGService(config)

result = rag.chat(
    user_id="user-001",
    session_id="conversation-001",
    question="Which projects have I worked on?"
)

Best suited for

  • Experiments and local development
  • Embedding RAG inside a Python application
  • Unit testing service logic directly
  • Simple single-process deployments
The snippet illustrates the integration pattern. Match the import path and method signature to the module version you run.

HTTP service boundary

The Streamlit frontend sends JSON requests to a FastAPI service. The API calls the RAG core and returns a structured answer, so clients never import the backend's Python package.

Streamlit / another client
          │ HTTP
          ▼
FastAPI :8000
          │
          ▼
RAGService ── Qdrant
          └── Ollama on host

Best suited for

  • Access from multiple computers
  • Independent frontend and backend deployments
  • Integration with other applications
  • Repeatable Docker-based deployment
  • A central RAG endpoint on a trusted LAN or VPN

In the demo setup the RAG API is exposed on port 8000, Qdrant on 6333–6334 and the Streamlit frontend on 8501. The API container reports a healthy status.

Local Ollama generation

Embeddings and answer generation both use Ollama-hosted models, keeping inference on your own machine or server.

Question → nomic-embed-text
         → Qdrant retrieval
         → local Ollama LLM
         → answer

OpenAI generation variant

Keeps local Ollama embeddings and Qdrant retrieval but sends answer generation to the OpenAI Responses API. It needs a backend-only OPENAI_API_KEY and incurs usage cost.

Question → local embedding
         → Qdrant retrieval
         → OpenAI Responses API
         → answer
04 / Pipeline

From documents to a grounded answer

STEP 01Prepare knowledge

Organize source text documents by topic and load them for ingestion.

STEP 02Chunk & embed

LlamaIndex prepares chunks and Ollama's nomic-embed-text turns them into vectors.

STEP 03Store vectors

Qdrant stores vectors with their text and metadata in a collection.

STEP 04Retrieve context

The question is embedded and similarity search returns the top chunks.

STEP 05Use memory

Recent history enriches retrieval for follow-up questions, with no extra LLM call.

STEP 06Generate answer

The configured LLM receives the question, history and retrieved context.

STEP 07Return response

The backend returns the answer, sources, scores and timing metrics.

STEP 08Continue session

The exchange is stored in the user/session memory namespace.

Simplified request lifecycle
User question
  → validate request and user/session identifiers
  → read recent session history
  → construct a contextual retrieval query
  → embed query using nomic-embed-text
  → search Qdrant (example top_k = 5)
  → build prompt with retrieved text + conversation context
  → call configured LLM
  → return answer, sources and timing information
  → update session memory

08 / Security

Security, privacy and reliability

What to put in place before exposing the service beyond a development LAN.

🔐 Protect model and service credentials

  • Never place API keys in frontend code or source control.
  • Use environment variables or a secrets manager for backend credentials.
  • Do not expose unauthenticated admin endpoints to the public internet.

🛡️ Restrict network access

  • Bind and firewall ports to match the deployment topology.
  • Prefer a trusted LAN or VPN for private deployments.
  • Do not expose Qdrant or Ollama to untrusted networks without securing them.

👥 Enforce session authorization

  • Validate user identity on the backend.
  • Do not trust a client-supplied user ID as authentication.
  • Verify users can only read their own history.
  • Use Redis or a shared store for multiple API workers.

📏 Evaluate answer quality

  • Inspect retrieved sources and test retrieval relevance.
  • Measure unsupported answers and hallucinations.
  • Log request IDs and structured errors without leaking data.
  • Set timeouts, rate limits and resource limits.
Privacy reminder: if the knowledge base holds personal or confidential information, retrieval and prompt instructions alone are not authorization controls. Apply access rules in the backend before returning sensitive content.
