01 / Overview

One operational view for traffic analytics and camera health.

◎

The challenge

Traffic analytics are spread across different event types and monitoring endpoints. Checking each source separately makes it harder to identify stale events, failed collection requests, unreachable devices and worker failures from one place.

↗

The solution

Independent Python workers poll configured endpoints and devices on a schedule. They store latest state and collection history in date-wise SQLite databases, while a Streamlit dashboard displays statuses, timestamps, search filters and available camera snapshots.

Design principle: collect independently, persist locally, supervise health, and present a unified view. The dashboard reads local database state; its refresh interval is separate from the collector schedule.
02 / Capabilities

What the platform monitors

⌁

ANPR events

Collects the latest plate-bearing event per configured device, including event ID, plate text, vehicle type, location and event timestamp.

▣

FOV snapshots

Requests JPEG snapshots for configured stream IDs, stores images in date/location folders and saves their paths and collection status.

⇢

Line crossing

Queries vehicle-crossing events by analytics zone and stores event, vehicle, zone, timestamp and image-path details.

⚑

Violation monitoring

Tracks configured helmet and seatbelt violation categories and maintains current-state and time-series records.

⌁

Network reachability

Connects to a remote host over SSH and runs ping checks against configured camera IP addresses, recording status and latency when available.

◉

Health supervision

Checks worker and event freshness, then sends webhook alerts on unhealthy-state transitions and a recovery notification when the system returns to healthy.

Conceptual data flow based on the supplied Python source files. The supervisor is launched by the master scheduler and reads the local monitoring databases.

Collection layer

Each worker owns a monitoring concern, loads shared camera configuration, requests data, normalizes fields and writes results to its corresponding database.

Presentation and alert layer

The dashboard presents local state. The supervisor separately evaluates timestamps and records its previous state to reduce repeated alerts while an incident remains active.

04 / Workflow

How a monitoring cycle works

01Schedule

The master process determines which worker is due and launches it as a subprocess.

02Collect

The worker authenticates or connects, requests the latest event/snapshot or runs a reachability check.

03Persist

Latest state and history are saved with collection status and request timestamps; event times are retained separately where available.

04Observe and alert

The dashboard renders local data while the supervisor checks freshness and sends incident/recovery notifications on state changes.

05 / Data design

Current state plus historical collection records

The database path utility creates date-wise folders using India Standard Time (UTC+05:30). The current tables support fast dashboard reads, while time-series tables retain repeated collection samples.

Event timestamp

Represents when the analytics platform says the event occurred. It is used to reason about event freshness.

Request timestamp

Represents when the collector checked or saved the result. A recent request with an old event can mean no new events have arrived.

07 / Operational value

Why this system is useful

For monitoring operators

  • View multiple traffic analytics streams from one dashboard.
  • Spot stale event timestamps and collection failures.
  • Review recent FOV snapshots when present.
  • Search and filter camera/device records quickly.
  • Receive webhook alerts for detected health-state transitions.

For engineering and maintenance

  • Separate the latest state from historical collection records.
  • Track worker run outcomes, errors and timeouts.
  • Compare event time with request time during investigation.
  • Keep data grouped into day-wise SQLite files.
  • Extend the modular worker pattern with additional checks.
Important distinction: ping success does not prove a video stream is healthy, and an old event does not alone prove a camera is offline. Use API status, worker logs, event freshness and network reachability together when investigating an incident.
08 / Reliability and security

Production considerations

Reliability improvements

Potential next steps include bounded retries with backoff, schema migrations, SQLite busy-timeout/WAL evaluation, database and image retention, and alerts for master-process or disk failures.

Security controls

Credentials and webhook secrets should be moved out of source files and rotated if exposed. Use verified SSH host keys, least-privilege accounts, restricted dashboard access, and careful handling of stored session cookies and plate data.
